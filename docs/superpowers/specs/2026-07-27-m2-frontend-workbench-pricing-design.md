## 1. 目标与范围

在后端生成/计费接口就绪**之前**，先把面向用户的两个核心界面做出来，用假数据驱动真实交互流程。目的是让产品决策（布局、信息层次、定价呈现）能被眼睛验证并低成本修改，同时让最容易出 bug 的加载与失败状态从第一天就真实运行。

**本轮做：**

| 交付物 | 说明 |
|---|---|
| `/generate` 工作台 | 左参数列 + 右结果区，完整的提交→等待→出图/失败流程 |
| `/pricing` 定价页 | 3 档订阅卡 + 加量包 + 双余额说明 |
| 顶栏余额显示 | 常驻右上角 |
| 余额不足弹窗 | 引导至 `/pricing` |
| 假数据 Route Handler | `models` / `plans` / `generations` |

**本轮不做：** `/history`、`/gallery`、管理后台、Stripe 接入、真实上游生成调用、R2 上传、OAuth。

**明确的取舍：** 定价卡上的档位差异点（优先排队、私密生成、商用授权、最高并发）是占位文案，上线前必须换成真能兑现的差异，否则构成虚假宣传。价格与次数同为占位值，改动只需改后端 `plans` 表，不涉及前端代码。

## 2. 关键决策与依据

### 2.1 生成接口是同步的，不是异步

上游网关（ezlinkai）对图像生成**同步返回结果 URL**，最慢约 3 分钟。异步是视频生成才需要的。

因此上游规格第 6 节设计的整套异步机制**全部不需要**，应从后续后端计划中删除：

- reconcile worker 长驻 goroutine、双通道回收、5 分钟兜底扫描
- `generations.upstream_task_id` 及其唯一索引
- `GET /generations/:id` 轮询接口
- 前端每 2~3 秒轮询的状态机

传输用**普通 JSON**，不用 SSE 流式。部署链路上只有自控的 nginx（调高 `proxy_read_timeout` 即可），**域名不经过 Cloudflare 橙云代理**，Cloudflare 仅用作 R2 对象存储，故其不可配置的 100 秒 524 限制不适用。

> 若将来把域名挂到 Cloudflare 代理后面，或部署到 Vercel Hobby（Route Handler 60 秒上限），此决定必须重新评估——届时需改为 SSE 流式心跳以绕开空闲超时。

### 2.2 同步模式引入的两个风险及缓解

计费正确性的要求没有因为同步而降低——扣费仍需条件原子更新，失败仍需退回且幂等。同步只是让幂等实现变简单（单请求事务内闭环，无需跨进程去重）。但同步引入了异步没有的两个风险：

**风险一：客户端断开导致扣费但丢图。** Go 中若用 `c.Request.Context()` 调上游，用户关闭标签页会取消请求 context，上游调用随之中断——次数已扣，图片丢失。3 分钟的等待窗口让"中途离开"从边缘情况变成常见情况。

> **对策：** 上游调用必须使用脱离请求生命周期的 context（`context.WithTimeout(context.Background(), …)`），服务端无论客户端是否还在都要完成并落库。

**风险二：进程崩溃或部署重启吃掉进行中的生成。** 异步方案有 worker 兜底，同步方案没有。

> **对策：** 调上游**之前**先落 `generations` 行（status=processing），服务启动时扫描处于 `processing` 的行并退款。这比 worker 简单一个数量级，但不可省略——省略即意味着用户付费未得图且无人知晓。

**衍生影响：** `/history` 的优先级应提前。同步模式下它是"关闭页面后找回图片"的唯一途径，应紧随本轮之后实现。

### 2.3 假数据用 Route Handler，不用 MSW，不用直接 import

沿用 M1 已有的 BFF 模式：新增 Route Handler 返回写死的 JSON，组件按真实流程调用同源接口。

接入真实后端时**只改这几个 Route Handler 内部**（把写死 JSON 换成 `lib/backend.ts` 调用），组件、类型、测试全不改动。

- 否决 MSW：它拦截浏览器请求，拦不到 Server Component 的服务端取数，等于要维护两套 mock。
- 否决直接 import：没有延迟、加载态、失败态，接 API 时工作台组件基本要重写。

### 2.4 界面决策及其调研依据

调研了 Midjourney、Leonardo、Ideogram、Krea、Playground、Freepik/Magnific、Recraft、Adobe Firefly 八家线上产品，以及本地参考项目 `image-refs/next-money`（可读源码）。

| 决策 | 依据 |
|---|---|
| **Prompt 锚定在参数列底部**，生成按钮内嵌其下 | Midjourney、Krea、Recraft、Firefly、Freepik 五家采用底部锚定；Ideogram（顶部条）、Leonardo（左栏顶部）为例外 |
| **生成按钮上静态标注本次消耗**（"生成 ◆ 2"） | 八家中仅 Leonardo（静态标签）与 Freepik（悬停显示）如此，属少数派——但这两家正是按模型差异定价的，与本产品处境相同。`next-money` 亦如此（按钮内容为 `提交文案 + PointIcon + Credits[模型]`）。采用 Leonardo 式静态标签，因悬停式会让从不悬停的用户完全看不到价格 |
| **余额常驻顶栏右上角** | Freepik、Recraft 确认在右上；Leonardo 在左上。Adobe Firefly 将余额藏进头像菜单并因此招致用户投诉，明确不效仿 |
| **参数列在左侧** | 证据矛盾：Leonardo（八家中参数最多者）在左，`next-money` 在右（`grid-cols-[1fr_240px]` + 面板 `order-2`），Firefly 官方截图与第三方教程互相矛盾且未能证实。由产品方决定为左侧 |
| **不用确定性进度条** | 上游不提供进度信号，画一条会走的进度条是欺骗。改为动画骨架 + 已用秒数（"已生成 42 秒…"）。Canva Apps 设计规范建议超过 5 秒的等待使用确定性进度条，但其前提是存在真实进度数据，此处不成立 |

## 3. 界面设计

### 3.1 `/generate` 工作台

```
┌────────────────────────────────────────────────────────┐
│ Image Studio | Generate  History  Gallery      ◆ 120次 │
├──────────────────┬─────────────────────────────────────┤
│ 模型             │                                     │
│ [Flux Pro · 2次▾]│                                     │
│ 比例             │         结果区                      │
│ [1:1][16:9][9:16]│    （骨架动画 + 已生成 42 秒…）     │
│ 参考图（可选）   │                                     │
│ [ 拖入图片     ] │                                     │
│                  │                                     │
│ ─────────────    ├─────────────────────────────────────┤
│ [描述你想要的…] │ 最近生成                            │
│ [生成 ◆ 2] [🔒] │ [▫][▫][▫][▫]                        │
└──────────────────┴─────────────────────────────────────┘
   240px 参数列              主区
```

- 参数列宽 240px，Prompt 与生成按钮固定在列底部
- 生成按钮旁为公开/私密切换（对应上游规格 `generations.is_public`）；将其置于此处的理由是按下生成的瞬间正是用户决定是否公开的时机
- 「最近生成」缩略条仅展示本次会话内的结果，不是历史页

### 3.2 `/pricing` 定价页

三张套餐卡横向排列，Pro 档高亮为锚点；下方加量包区；底部双余额说明段。

| 档位 | 月费 | 每月次数 | 折合每次 |
|---|---|---|---|
| Starter | $9 | 200 | $0.045 |
| Pro（高亮） | $29 | 800 | $0.036 |
| Max | $99 | 3000 | $0.033 |

加量包（不过期，仅订阅用户可买）：$5 / 100 次，$20 / 450 次，$50 / 1200 次。

**每张卡必须标注"约 $0.0XX 每次"**——这是让价格梯度可见的唯一办法。不标则用户需自行计算，多数人不会算，"越贵越划算"的机制随之失效。

**双余额规则单独成段，用大白话写**，不塞进 FAQ：

- 月度次数随订阅每月**重置**，用不完不累积到下月
- 加量包次数一次性购买，**永不过期**，取消订阅后仍保留
- 生成时**优先扣月度次数**，月度用尽才动加量包

这三条若不讲清楚，用户看到余额变化会认为被多扣，是最容易产生工单与差评之处。

## 4. 假数据状态机

**不使用随机**。用 prompt 关键词做确定性触发，使每条失败路径都能稳定复现并自动化测试。

| prompt 内容 | 行为 |
|---|---|
| 普通文本 | 15 秒后返回成功，附占位图 URL |
| 含 `fail` | 8 秒后返回失败，**退回已扣次数** |
| 含 `slow` | 90 秒后返回成功（验证长等待体验与客户端超时提示） |
| 余额不足 | 立即返回 `40001`，前端弹升级窗 |

次数在服务端内存中真实扣减，失败真实退回。余额通过 `GET /api/credits` 读取，顶栏与工作台共用。

内存状态在开发服务器重启后重置，这是可接受的——它同时也演示了真实系统里"重启丢失进行中任务"的问题，对应 §2.2 风险二。

## 6. 错误处理

沿用 M1 认证阶段已踩过坑并修复的模式：

| 情况 | 处理 |
|---|---|
| 网络故障（fetch reject） | 所有 `fetch` 必须带 `catch` 并显示可见错误。M1 曾因缺失 `catch` 导致表单静默失效——按钮闪一下即复原、无任何提示，与未点击完全一致 |
| 生成失败 | 结果区显示失败原因，并明确告知"已退回 2 次" |
| 余额不足（40001） | 弹窗说明并深链至 `/pricing` 加量包区 |
| 客户端超时 | `AbortSignal.timeout(240_000)`（覆盖 3 分钟最慢模型并留余量），超时显示明确提示而非无限等待 |
| 服务端错误 | 不向用户展示内部诊断信息。`app/error.tsx` 错误边界已在 M1 建立 |

## 7. 测试方式

**单元测试（Vitest）** —— `lib/fixtures.ts` 的状态机为纯函数，可直接测：

1. 余额充足时扣减正确，余额快照与流水一致
2. 余额不足时拒绝且不扣减（边界：恰好等于所需次数应通过）
3. 失败任务退回次数，且重复退款调用不会二次入账（幂等）
4. 扣费与退款的先后顺序不影响最终余额

**端到端（Playwright）** —— 三条路径：

1. 提交普通 prompt → 骨架与秒数计数出现 → 15 秒后结果图显示 → 余额减少
2. 提交含 `fail` 的 prompt → 显示失败原因 → 余额恢复原值
3. 余额耗尽后提交 → 弹出升级窗 → 点击跳转 `/pricing`

沿用 M1 的约定：`workers: 1` 串行执行；断言 `role=link` 以守住顶栏导航的无障碍语义（历史教训见 `README.md`）。

## 8. 接入真实后端时需要改什么

只改 `app/api/` 下四个 Route Handler 的内部实现——把写死的 JSON 替换为 `lib/backend.ts` 调用，并删除 `lib/fixtures.ts`。

组件、类型、单元测试之外的端到端测试均不改动。这是选择 Route Handler 假数据方案的全部意义。

后端侧对应需实现（不在本轮）：`GET /models`、`GET /plans`、`GET /me` 扩展双余额、`POST /generations`（同步）、`credit_accounts` 与 `credit_transactions` 表及条件原子扣费。

## 9. 已知遗留

- 定价卡档位差异点为占位文案，上线前必须替换为可兑现的真实差异
- 价格与次数为占位值
- 登录接口无速率限制（前后端皆无），上线前必须补
- 顶栏在根布局读 cookie 导致所有路由动态渲染，落地页无法预渲染或走 CDN 缓存（M1 遗留，见 `README.md`）
- `/history` 因同步模式而重要性上升，应紧随本轮实现
